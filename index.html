FreeRTOS concepts used in this project

Every concept here is real code on the board with a real job. The live part of each card updates from the ESP32's reports.

Tasks and cores

4 tasks on 2 cores

A task is a small program with its own stack. The ESP32-S3 has two cores, so two tasks can truly run at the same moment.

Here: MqttTask and the Wi-Fi driver use core 0. SensorTask, CommandTask, ButtonTask and the button interrupt use core 1, so network work never delays sensor reading.

Queues

dataQueue, cmdQueue, outQueue

A queue passes copies of data safely from one task to another. The receiving task sleeps until something arrives.

Here: readings go SensorTask → MqttTask, commands go MqttTask → CommandTask, and replies plus button events go back to MqttTask.

Mutex

serialMutex

A mutex is a lock that only one task can hold at a time. The task that takes it must give it back.

Here: all four tasks print to the same Serial port. Without the mutex, their lines would mix into each other.

Interrupt + binary semaphore

buttonISR → buttonSem → ButtonTask

An interrupt (ISR) must finish in microseconds, so it only gives a binary semaphore. ButtonTask, blocked on that semaphore, wakes up and does the real work.

Here: pressing the BOOT button (GPIO 0) asks for an instant reading.

Task notifications

The lightest way to wake one task

A task notification wakes one specific task directly, with no queue or semaphore object in between.

Here: ButtonTask notifies SensorTask ("read now"), and the timer notifies MqttTask ("send the report").

Event group

netEvents

An event group is a set of on/off flags (bits) that tasks can set, clear and wait for.

Here: MqttTask sets WIFI_OK and MQTT_OK. SensorTask waits for WIFI_OK before it starts reading.

Software timer

sysTimer, every 5 s

A software timer runs a callback function from the FreeRTOS timer task, so it needs no task of its own.

Here: it takes a snapshot of all tasks and the CPU load, then notifies MqttTask to send the system report.

Priorities and pre-emption

Who gets the CPU first

Each task has a priority. When a higher-priority task becomes ready, FreeRTOS pre-empts (pauses) the lower one on that core straight away.

Here: ButtonTask has the highest priority, so a button press is handled at once, ahead of SensorTask and CommandTask on core 1.

Stack and heap memory

Every task has its own stack

Each task gets a fixed stack when it is created. The high-water mark shows the smallest amount that was ever left free. Near zero means the stack could overflow.

Here: the sizes were chosen so every task keeps a safe margin. Queues, the mutex and the timer are allocated from the heap.
